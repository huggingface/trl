### Architecture and training backend

- Ray single controller. vLLM engines (`--vllm.num_engines`, `--vllm.tensor_parallel_size`) are Ray actors wrapping `vllm.AsyncLLMEngine`. The policy trains with **DeepSpeed** (ZeRO stage via `--ds.zero_stage`, default 2; every math example uses ZeRO-3, bf16). FSDP is not an option in this repo; the README advertises a separate "Molt" (NeMo Automodel) backend in another repo, which we don't use.
- Master weights: DeepSpeed `bf16.enabled` → bf16 model params with an fp32 master copy in the optimizer (DeepSpeed's bf16 optimizer).
- Weight sync to vLLM: NCCL group between DeepSpeed rank 0 and every vLLM rank; under ZeRO-3 each parameter is all-gathered to rank 0 then broadcast (`ppo_actor.py: broadcast_to_vllm`). CUDA IPC only when colocated and not async.
- Old logprobs are recomputed by an extra actor forward pass on every batch (`experience_maker.make_experience`), not taken from vLLM. vLLM logprobs are requested only when IS correction is on (`--algo.advantage.is_correction_level token|seq`).

### Async mode (README "Execution modes" table + `trainer/ppo_trainer_async.py`)

- Three modes: Hybrid Engine (colocated, strictly on-policy, "most stable"; what all the math recipes use), **Async** (`--train.async_enable`, `--train.async_queue_size N`, default 1, "highest throughput"), and Async + partial rollout (`--train.partial_rollout_enable`, vLLM pause/resume instead of a lock, "most aggressive off-policy", pair with token IS correction).
- Mechanics: a generator Ray actor and a trainer Ray actor share a `ray.util.queue.Queue(maxsize=queue_size)` plus a slot semaphore. Without partial rollout, a `VLLMLock` makes generation of a whole batch and the weight broadcast mutually exclusive, so every sample in a batch comes from one policy version. With queue size 1 the generator produces batch k+1 on weights v_k while the trainer trains on batch k, so max staleness is 1 step; the broadcast after step k waits until batch k+1 finishes generating.
- The README warns: "Asynchronous training may affect training stability. Use it only when throughput is critical and convergence is validated." The async example (`train_reinforce_baseline_ray_agent_async.sh`) uses async + partial rollout + token-level IS correction (`mask`, ICEPOP) with REINFORCE++-baseline.
- Recommended async setting we use for W1: `--train.async_enable --train.async_queue_size 1` (README default, no partial rollout), so max staleness = 1.

### Algorithms

- `--algo.advantage.estimator`: `gae` (PPO), `reinforce`, `reinforce_baseline` (README: "best for RLVR"; group mean subtracted, then batch-level whitening), `rloo`, `group_norm` (GRPO: (r - mean)/std per group), `dr_grpo` (group mean only, no std, no batch whitening), `flash_reinforce`.
- Loss: PPO clip with `--actor.eps_clip_low_high` (asymmetric), `--actor.loss_agg_mode token-mean` (default; global token mean over the whole optimizer step across DP ranks and micro-batches, see `utils/loss_utils.py`), optional KL loss (`--algo.kl.use_loss`, `--algo.kl.init_coef`; a reference model is only created when `init_coef > 0`), entropy coef, IS correction (`is_correction_level/mode/threshold`, default band [0.5, 5]).
- Optimizer defaults are not ours: AdamW betas (0.9, 0.95), `cosine_with_min_lr` scheduler with 3% warmup and min_lr 0.1×. We override them for W1.

### Math recipes and published numbers

- `examples/scripts/train_prorlv2_math_hybrid_engine.sh` (ProRL v2): DeepSeek-R1-Distill-Qwen-1.5B, `OpenRLHF/dapo-math-17k`, REINFORCE++-baseline, clip 0.2/0.27, KL k2 loss 1e-4, dynamic filtering, token IS mask [0.5, 5], 512 prompts × 16 samples per rollout, train batch 1024 (8 optimizer steps per rollout), 8192 new tokens, lr 1e-6, colocated hybrid engine on 1 node × 8 GPUs, AIME-2024 eval every 5 steps (temp 1.0, 4 samples). This is the closest published math recipe.
- `train_dapo_ray_hybrid_engine.sh`, `train_reinforce_baseline_ray_agent_async.sh` (Qwen3-4B-Thinking, 64k tokens), `train_vlm_math_hybrid_engine.sh` (Qwen3.5-2B on geometry3k with images, eager attention, no packing).
- Published numbers: the repo has none (no curves or result tables in README or docs). The ProRL v2 NVIDIA blog only gives bar charts after 2,000-3,000 steps, no early-step values. The REINFORCE++ paper reports math results (e.g. Qwen2.5-Math-7B on MATH levels 3-5, 32 prompts × 8, lr 5e-7: MATH-500 72.0) without saying which framework ran them, except the ZeroTIR agent table, which used OpenRLHF. ### Qwen3.5 (hybrid gated DeltaNet, VLM checkpoint) in the code

- `utils.is_vlm_model` checks for `vision_config`, so Qwen3.5 loads as `AutoModelForImageTextToText` in the trainer (full VLM incl. vision tower); `--actor.freeze_visual_encoder` freezes everything outside `language_model.*` / `lm_head.*`. vLLM loads the checkpoint itself.
- `models/utils.set_z3_leaf_modules` has a note that marking Qwen3.5 hybrid decoder layers as ZeRO-3 leaves silently froze ~390/417 params, so hybrid leaf detection is off by default.
- Packing (`--ds.packing_samples`) is refused only when images are present (`max_images_per_prompt > 0`). Text-only Qwen3.5 can pack. Packing unpads to one `[1, total]` row with per-sample `position_ids` and `attention_mask=None`; full-attention layers then use flash-attn varlen. Whether the linear-attention layers see sample boundaries is decided by transformers' Qwen3.5 code, checked below.
- The VLM example comment says: "Use --ds.attn_implementation eager for models with linear attention (Qwen3.5). Flash attention may not support packed sequences with linear attention layers."

19. **The two W1-S hangs (364409 at step 48, 364704 at step 8) were the reward, not the trainer OOM.** What the logs show: in both runs the trainer's last step finished on rank 0 (`Train epoch [1/1]: 100% 64/64`), which needs every rank in the gradient reduce-scatter, so no trainer rank had died or wedged; the allocator warnings before it were recovered retries (item 20). The trainer then sat in `broadcast_to_vllm`, which waits on the VLLMLock that the generator holds until its batch is complete, and generation stopped at 24/32 groups (364409) and 31/32 (364704). No actor error, traceback or `ActorDied` in either log. In async mode the 32 prompts of a batch are spread over the 4 engines by pending-request count, so each engine gets 8: 24/32 is exactly one engine's share missing, 31/32 one group. Mechanism: OpenRLHF runs `reward_func` with `asyncio.to_thread` inside each vLLM rollout actor (`utils/agent.py: _fetch_rewards_via_func`), so the shared reward's math_verify runs off the main thread with its SIGALRM timeouts off. An answer like `\boxed{9^{9^{9}}}` makes sympy evaluate a huge integer power in C, which holds the GIL, so the actor's event loop (which drives all of that engine's requests and returns their results) stops. `envs/openrlhf/reward_gil_check.py` (CPU jobs 364740, 364770) runs the old adapter (`envs/openrlhf/w1_reward_orig.py`) under `asyncio.to_thread` with a 50 ms ticker: `9^{9^{9}}`, `10^{10^{10}}` and `99999999999^{99999999999}` never return within 60-120 s and the loop never ticks once (0 ticks); `(10^{9})!` ticks for 34 s (Python-level parsing), then the loop freezes; `1000000!` returns after 4.6-6 s with a 1.9-2.5 s loop stall. I can't name the exact completion that froze each run (no rollout dump, no stack: ptrace is restricted), so this is the mechanism that fits both stall shapes, not a captured trace. Fix in our adapter `configs/openrlhf/w1_reward.py`: `compute_score` (unchanged) runs in an 8-process spawn pool per rollout actor, on each worker's main thread, so math_verify's 5 s timeouts are on (as for the reference on its main thread), plus a 30 s hard kill of the pool for anything that ignores SIGALRM. With it, every case above returns 0.0 in 6.0-6.5 s with the loop never stalling more than 0.1 s; normal answers score as before (1.1 s on a cold pool, then ms). Calls over 3 s are logged (`w1_reward: slow compute_score`) so the next run records the answers that would have frozen the actor. No OpenRLHF source change. Any library that calls `compute_score` from a non-main thread or an event loop has the same exposure; OpenRLHF's own default (`--reward.remote_url` file run via `asyncio.to_thread`) offers no timeout or process isolation for a custom reward.

Allocator warnings (`CUDACachingAllocator ... memory allocation failed with OOM ... trying to allocate ~16.5 GB`, 22 in 364409, 3 in 364704): 16.5 GB is the fp32 logits of one ~16.6k-token micro-batch (16.6k × 248320 × 4 B). `Actor.forward` always casts the full logits to fp32 and computes log-probs on the whole tensor (`models/actor.py` L267, flash-attn's Triton cross entropy); OpenRLHF has no chunked-logprob or fused linear-CE option for this path (`--ds.use_liger_kernel` is refused for VLM checkpoints, and Qwen3.5 loads as one), batch sizes are already 1 and gradient checkpointing is on, which is everything its README lists under "When hitting OOM". With free memory at 3-9 GB of 191 GB at the time of each warning on a 2B model, this is caching-allocator fragmentation from micro-batches of varying length rather than live tensors, and each warning was a recovered retry (training continued). Fix: `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, exported in `launch/openrlhf/common.sh` before `ray start` so every actor inherits it (an env var, not a training knob; `PYTORCH_CUDA_ALLOC_CONF=` restores the default). Not a cause of the hangs (item 19).

A 9B save costs ~110-125 s: a 119 GB DeepSpeed `_actor` checkpoint (ZeRO-2 optimizer state, max 1 kept) in ~70 s, then an 18 GB HF dir in ~25 s. Disk per run: 4 x 18 GB HF + 119 GB DeepSpeed ≈ 190 GB. One smoke covers both arms: the recommended arm adds a ~19 GB reference replica, which gives ~130 GB at most, under 180.

## W2-M (agentic TermGrade, Qwen3.5-9B)

1. Recipe source: README "Multi-Turn Agent" (`--train.agent_func_path`, `--train.async_enable`) and `examples/python/agent_func_openai_server_executor.py` (README's route for external OpenAI-API agents such as terminus-2). 2. Harness glue `configs/openrlhf/w2_agent.py`: an `AgentExecutorBase.execute` (README's "fully custom token-level execution" route) that runs each episode on the same OpenEnv Harbor server as TRL/verl (terminus-2, local Apptainer boxes, 8 shards, `harbor_serve.py` step limit), proxies terminus-2's chat calls to OpenRLHF's own vLLM actor, keeps sampled tokens and tokenizes only new messages (as MultiTurnAgentExecutor), one sequence per episode, loss only on sampled tokens. No OpenRLHF source patch.
3. CPU check (job 379435): delta tokenization appends exactly `\n<|im_start|>user ... <|im_start|>assistant\n<think>\n\n</think>\n\n`; scripted replays of 3 solved verl episodes score 1.0, nop episodes 0.0 (parity with the verifier).
4.
