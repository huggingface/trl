# miles: notes

miles = RadixArk's fork of slime: Megatron-LM trainer + SGLang rollout, Ray orchestration. Repo https://github.com/radixark/miles, pinned at release `v0.1.3` (2026-10-22). Docs are in the repo under `docs/` (also served at miles.radixark.com/docs). Everything below was read from the v0.1.3 tree or main as of 2026-11-09 (`778794a8`); where they differ it says so.

## Research (task 1)

### Install

- Recommended path is the Docker image (`docs/getting-started/installation.md`: "Docker is recommended because Miles pins patched versions of SGLang, Megatron-LM, and a few CUDA kernels"). The from-source path is `pip install -r requirements.txt && pip install -e . --no-deps` into an env that already has their patched SGLang (`sglang-miles` branch) and Megatron-LM (`radixark/Megatron-LM` `miles-main`), plus a set of prebuilt CUDA wheels (TE `2.17.0+miles`, causal-conv1d, DeepGEMM, FA3...) from `radixark/miles-wheels`. The docs warn that installing those yourself at the wrong commit is "the most common source of bug reports". So we use the image, imported with Enroot and run through Pyxis. No venv; `envs/bench-miles` is not created.
- Image: `radixark/miles:v0.1.3` (multi-arch amd64/arm64, 23.3 GB compressed). Release versions freeze SGLang and Megatron commits in `release-lock.json`: SGLang `sgl-project/sglang@3a938213` (`sglang-miles` branch, on base image `lmsysorg/sglang:v0.5.22`), Megatron-LM `radixark/Megatron-LM@2fbe25a4`. Torch 2.14 cu130 wheels set, TransformerEngine `2.17.0+miles`, `flash-linear-attention==0.5.2`, `causal-conv1d==1.6.1`, `mamba-ssm==2.3.1`, `transformers==5.19.0`, mbridge + Megatron-Bridge at pinned commits.
- The image's own miles checkout is at `/root/miles` (editable), Megatron at `/root/Megatron-LM`, SGLang at `/sgl-workspace/sglang`. All three are editable installs.
- `latest`/`dev` move daily (rebuilt within ~30 min of any SGLang/Megatron branch move); we don't use them.

### Hardware

- `installation.md` lists "NVIDIA GB300 / GB200 / B300 / B200: Production". The image is built for cu130 and the wheels include sm_100 builds. FlashQLA (alternative GDN kernel) needs SM90+; default GDN backend is fla (Triton), which is arch-portable. On Blackwell miles sets `NVTE_FP8_BLOCK_SCALING_FP32_SCALES=0` automatically (only relevant for FP8).

### Fully async mode and its recommended off-policy setting

- `train_async.py ... --fully-async` (`docs/user-guide/fully-async.md`, `miles/rollout/fully_async_rollout.py`). A persistent rollout worker keeps generation in flight and pushes finished groups into a bounded buffer; the trainer drains `--rollout-batch-size` groups per step; weights sync every `--update-weights-interval` steps (default 1) with generation paused (`--pause-generation-mode`; default `retract`, the reference example uses `in_place` because "retract can deadlock flush_cache in fully_async under load").
- In-flight cap: `--rollout-batch-size` groups by default (or `--async-max-concurrent-samples`). Slots free per sample (`--rollout-submission-granularity sample`, the fully-async default).
- Off-policyness: buffer capacity `--async-data-buffer-capacity-factor` default 2.0 x rollout_batch_size groups; `--max-weight-staleness` is **unset by default** (no staleness filter). `--async-submit-within-staleness` (off by default) turns it into an AReaL-style admission bound.
- Off-policy correction: the reference fully-async recipe (`examples/infra_features/fully_async/run_qwen3_5_4b_fully_async_eval.py`) adds `--use-tis` (truncated importance sampling on the train/rollout logprob ratio). `train_async.py` calls `validate_async_off_policy_correction(args)` at startup.
- So "recommended default" for us = reference example: `--fully-async --pause-generation-mode in_place --use-tis`, buffer factor 2.0, no staleness cap. The effective max staleness is bounded by the buffer: at most ~2-3 versions in steady state (measured, see runs).

### Megatron defaults for small dense models

From `scripts/run_qwen3_dense.py` (the quick-start launcher; covers Qwen3-4B, Qwen3.5-4B/9B/27B):

- Qwen3.5-4B / 9B: TP=2 + sequence parallel, PP=1, CP=1, full recompute (`uniform`, 1 layer), dynamic batch with `--max-tokens-per-gpu 9216`, `--attention-backend flash`, grads accumulated in fp32. SGLang engines TP=1 (`--rollout-num-gpus-per-engine 1`), because SGLang TP>1 produced garbage for Qwen3.5 on 0.5.9 (sglang#21039), `mem-fraction-static` 0.7.
- The quick-start runs colocated (`--colocate`, `train.py`). The fully async example uses 4 actor GPUs (TP=2, so DP=2) + separate rollout GPUs.
- GRPO block shared by every recipe: `--advantage-estimator grpo --use-kl-loss --kl-loss-coef 0 --eps-clip 0.2 --eps-clip-high 0.28`, Adam lr 1e-6 constant, wd 0.1, betas (0.9, 0.98). `--rollout-batch-size 32 --n-samples-per-prompt 8 --global-batch-size 256 --rollout-max-response-len 8192 --rollout-temperature 1`. That is very close to SHARED_W1 already.

### SGLang

v0.1.3 image: `lmsysorg/sglang:v0.5.22` base with the `sglang-miles` branch at `3a938213` checked out editable over it. Qwen3.5 (`Qwen3_5ForConditionalGeneration`) is served natively by SGLang including its vision tower; miles syncs only the text weights (`--check-weight-update-skip-list visual` in their Qwen3.5 CI test, comment: "miles has no Qwen3.5 vision implementation on the training side, so vision weights are never synced").

### Checkpoint conversion

- HF -> Megatron: `tools/convert_hf_to_torch_dist.py` with the model's Megatron args (`scripts/models/<type>.py`), run under torchrun on GPUs, writes a `torch_dist` checkpoint used as `--ref-load` (and as the initial actor weights when `--load` is empty). The HF dir is still needed: SGLang reads it and the model spec reads its config.
- Megatron -> HF: `--save-hf <path with {rollout_id}>` writes an HF checkpoint at each `--save-interval` (default `--megatron-to-hf-mode raw`: miles' own converters, the same ones the weight sync uses; it copies config/tokenizer files from `--hf-checkpoint`). Offline: `tools/convert_torch_dist_to_hf.py`. For Qwen3.5 the export contains only the text weights; see the smoke test for whether vLLM loads that against the VLM config.
- No Qwen3.5-2B Megatron args ship (0.8B, 4B, 9B, 27B do). 2B = 0.8B args with `--hidden-size 2048 --ffn-hidden-size 6144` (checked against the Hub config: 24 layers, 8 heads / 2 KV, head_dim 256, GDN 16 key / 16 value heads x 128, full attention every 4th layer, tied embeddings). We pass the args inline rather than adding a file to the image.

### Qwen3.5 hybrid support (read from code)

- `miles_plugins/models/qwen3_5.py` swaps every `linear_attention` layer of the Megatron GPT spec for a GatedDeltaNet module (`miles_plugins/models/linear_attn.py`); full-attention layers stay Megatron/TE with `--attention-output-gate`.
- GDN recurrence: `fla.ops.gated_delta_rule.chunk_gated_delta_rule` (default `--linear-attention-backend fla`; `flashqla` optional). Short conv: fla's `causal_conv1d` with backend "mix" (Triton forward, causal-conv1d CUDA backward) when causal-conv1d's backward imports, else Triton; logged as `Linear-attention short conv backend: ...`. There is no pure-torch fallback path: if fla is missing it raises.
- Packing: default `--qkv-format thd` (packed sequences). The GDN layer takes `packed_seq_params.cu_seqlens_q` and passes `cu_seqlens` to both the conv and the recurrence, so state does not leak across sample boundaries. CP>1 is supported for GDN only with fla.
- Text-only: the Megatron model is the language model only; `A_log` is kept in fp32 (`mark_param_dtype`). The rollout engine still has the vision tower (unused, never updated).

### W2 connectors (feasibility only)

- Connectors: Harbor (agent function), OpenEnv (agent function), NeMo Gym, Verifiers (rollout function), HUD (generate function), Strands, tau-bench. All marked experimental.
- Harbor: `examples/experimental/harbor` (in-process: `Trial.run()` inside the rollout worker, sandbox on a cloud provider) or `examples/swe-agent-harbor-docker` (agent server with a local Docker daemon, not usable here). Needs Harbor from the `harbor-miles-v0.20.0` branch of `harbor-framework/harbor` ("the terminus-2 truncation policy it carries is required for TITO"), installed with `uv pip install "harbor[<provider>] @ git+...@harbor-miles-v0.20.0"`. The sandbox backend is `HARBOR_ENV_TYPE`, passed straight to Harbor's `EnvironmentType`.
- HF Sandboxes: Harbor `main` has `EnvironmentType.HF_SANDBOX = "hf-sandbox"`, but the `harbor-miles-v0.20.0` branch does not (its enum stops at docker/daytona/e2b/modal/.../skypilot). So Harbor + HF Sandboxes in miles needs either the HF sandbox environment backported onto the miles branch or the miles terminus-2 changes forward-ported to Harbor main. miles' credential registry (`miles/rollout/agentic/credentials.py`, `PROVIDER_CREDENTIALS`) also needs one entry for it. Host-process agents (terminus-2) call the model from the worker, so no sandbox-to-cluster egress is needed; in-sandbox agents would need the session-server ports reachable from HF.
- OpenEnv: `examples/experimental/openenv` drives the tbench2 env (`OpenEnv/envs/tbench2_env`, needs OpenEnv >= the #1025 merge, `38b2a3135`) with one cloud sandbox per episode on Daytona / E2B / Modal / Novita (one `tb2_sandbox_<provider>.py` + `openenv_<provider>_agent_function.py` per provider), or against "one shared Docker env server". An HF Sandboxes backend would be a new `tb2_sandbox_hf.py`; alternatively the shared-env-server mode could point at an OpenEnv Harbor server we run ourselves on HF sandboxes (what the TRL side uses).
- Verified providers (docs table): AgentENV, Daytona, E2B, Modal, Novita. HF Sandboxes is not one.
- Verdict: W2 on miles is feasible but not off the shelf with HF Sandboxes: either a small Harbor backport (HF sandbox env onto `harbor-miles-v0.20.0`) or an OpenEnv shared-server setup. Both are a few files, not a library patch.

## Setup log (problems and fixes, in order)

1. **Launcher kills other jobs' processes on shared nodes.** miles' Python launchers (`scripts/run_*.py` -> `command_utils` Ray backend) run `pkill -9 sglang; ray stop --force; pkill -9 ray; pkill -9 miles; pkill -9 redis` before starting Ray. Enroot/Pyxis containers share the host PID namespace and every agent runs as the same user, so on a shared smoke node this would kill the other libraries' Ray and SGLang processes. Fix: we don't use the launchers. `launch/miles/common.sh` starts a private Ray head on ports derived from the job id (`--temp-dir /tmp/ray` is the container's private tmpfs) and runs `train.py` / `train_async.py` directly with the env vars the launcher would have put in the Ray runtime env (`PYTHONUNBUFFERED`, `CUDA_DEVICE_MAX_CONNECTIONS=1`, `NCCL_NVLS_ENABLE=1`, `MASTER_ADDR`, `PYTHONPATH` with `/root/miles:/root/Megatron-LM`). Flags are copied verbatim from the launcher scripts.
2. **No Megatron args for Qwen3.5-2B.** miles ships `scripts/models/qwen3.5-{0.8B,4B,9B,27B}.py`. 2B differs from 0.8B only in `hidden_size` 2048 and `intermediate_size` 6144 (checked against the Hub config), so `common.sh:model_args qwen3.5-2B` is the 0.8B string with those two values.
3. **`math-verify` is not in the image.** The shared reward needs it. Installed `math-verify==0.8.0`, `latex2sympy2_extended==1.10.2`, `antlr4-python3-runtime==4.13.2` with `uv pip install --target /fsx/amine_dirhoussi/envs/bench-miles --no-deps` (`envs/miles/prep_w1.sh`); `common.sh` appends that dir to `PYTHONPATH` only when the image can't import `math_verify`, so nothing in the image is shadowed. Reward self-test passes.
4. **W1 data format.** miles reads `--input-key` as either a string or a message list and applies the chat template. `configs/miles/prepare_w1_data.py` turns `train.parquet` into `messages` (one user message with the SHARED prompt) + `label`, same rows and order (17,255 rows).
5. **Image import preempted twice on hopper-cpu.** `enroot import` of `radixark/miles:v0.1.3` (23.3 GB compressed, 114 layers) was preempted at 18 min (job 364052, `--qos=low`, during layer extraction and then during squashfs creation) and requeued from scratch each time. Fix: cancelled; `install.sh` now runs at the top of the first GPU job (`launch/miles/smoke.sbatch`) when the `.sqsh` is missing.
6. **The source checkout is slow on /fsx.** `git checkout v0.1.3` of a 367-commit-older tag took ~4 min on /fsx (many small files). Harmless, just slow.
7. **Truncated image after preemption.** `enroot import -o` writes the squashfs straight to its final path, so the preempted import left a partial `miles-v0.1.3.sqsh`; the first smoke (job 364154) saw the file and Pyxis failed with `Invalid image format`. Fix: `install.sh` imports to `.sqsh.part` and renames on success.
8. **CUDA extension builds (coordinator note: no compiler or CUDA toolkit on hopper-cpu).** Not applicable to miles: causal-conv1d 1.6.1, mamba-ssm 2.3.1, fla 0.5.2, TE `2.17.0+miles` etc. come prebuilt in the image (`radixark/miles-wheels` cu130-torch214 release), and the only thing we install outside it is pure-Python math-verify. Nothing compiled, so no wheel to share in `stable-bench-src/wheels/`. The smoke job imports `causal_conv1d` and `fla` inside the container on a B200 to confirm they load (job 364156: `causal_conv1d 1.6.1`, `fla 0.5.2`, torch `2.14.1+cu130`). The shared `torch2.11-cu130-py312` causal-conv1d 1.7.0 wheel does not match the image torch and is not used.
9. **Silent 15-minute "hang" in checkpoint conversion = 2 GiB / 1 CPU srun step.** In smoke 364156, `convert_hf_to_torch_dist.py` for the 0.8B sat with no output and no CUDA context for 15+ min. py-spy can't attach (no ptrace on the nodes), so we read /proc on the node instead: ~2,000 major page faults/s, 275 s system time vs 1 s user, and the step cgroup `step_0/user/memory.max = 2147483648` even though the job had 496 GB. Cause: `b200-queue` submits from a hopper-cpu waiter job (`-c 1 --mem=2G`) with the default `--export=ALL`, so `SLURM_MEM_PER_NODE=2048`, `SLURM_CPUS_PER_TASK=1`, `SLURM_TRES_PER_TASK=cpu=1` end up in the GPU job's environment and `srun` applies them to the step. Fix: every miles sbatch unsets those vars and runs `srun --mem=0 --cpus-per-task=$SLURM_CPUS_ON_NODE`. Reported to the coordinator, since it hits any library that uses `srun` (e.g. Pyxis containers) inside b200-queue jobs. Also added `launch/miles/fh_wrap.py`, which dumps every converter rank's Python stack every 10 min, so the next silent stall is diagnosable.
10. **`--attention-backend flash` (the recipe setting) crashes in backward on B200 for Qwen3.5.** Smoke 364222, phase B (their Qwen3.5-0.8B CI recipe): `AssertionError: SM100 backward with head_dim=256 does not support local attention` from `flash_attn/cute/sm100_hd256_2cta_fmha_backward.py` (FA4), reached through TE from Megatron's flash backend. Qwen3.5's full-attention layers have head_dim 256. The same step logged trainer logprobs at -1.87/token against SGLang's -0.39 for the same tokens, so the forward on that path looks wrong as well. Their CI runs this test on H200 (FA3 path), so B200 isn't covered. Fix: `--attention-backend fused` (TE cuDNN fused attention) for Qwen3.5 on B200; checked below by whether the trainer/rollout logprob gap closes.
    Result with `fused` (smoke 364229, same recipe): trainer logprob -0.3607 vs SGLang -0.3601 at step 0, so the gap closes and the `flash` path on B200 was computing a wrong forward, not only failing in backward. `configs/miles/w1-S.args` and `launch/miles/repro.sbatch` use `--attention-backend fused`, a deviation from the recipe's `flash` that the hardware forces. (Qwen3-4B in the repro has head_dim 128, which may be fine on `flash`; we use `fused` there too rather than spend budget checking.)
11. **`fused` is not a fix either: no backward kernel.** With `--attention-backend fused` the step-0 logprobs match, but the first backward fails: `ValueError: No dot product attention backend is available for the provided inputs` (TE/cuDNN on sm100 has no head_dim-256 backward for this shape). The forward-only logprob computation worked, which is why the gap looked closed. miles' Gemma 4 recipe uses `unfused` + `--qkv-format bshd` for large head dims, but that drops sequence packing, so we didn't take that route.
12. **Root cause of 10, and the patch.** Read from the image (files extracted with `unsquashfs` in a CPU job): TE `2.17.0+miles` calls FA4 (`flash-attn-4 4.0.0b35`, `flash_attn.cute.interface`) with `causal=True, window_size=(-1, 0)`. FA4's `_resolve_causal_local_window` only treats `None`, or both sides negative, as "no window", so `(-1, 0)` becomes **local** attention with left window -1. Result: a wrong forward (wrong mask), and on head_dim 256 the SM100 backward assert. Patch: `configs/miles/fa4_window_fix/sitecustomize.py`, put first on `PYTHONPATH` by `common.sh` (so Ray workers inherit it). A post-import hook wraps `_resolve_causal_local_window` to map a negative window side to `None`. No library file is edited. Verified in smoke 364268 with `launch/miles/fa4_check.py` (FA4 called exactly as TE calls it vs torch SDPA, causal, head_dim 256, bf16): unpatched forward max abs error 3.875 and the backward asserts; patched forward error 0.0039, backward runs (dq/dk/dv max abs error 0.03/0.06/0.03 on a sum-of-squares loss, bf16). With the patch the recipe's `--attention-backend flash` is used again everywhere. This bug hits any miles v0.1.3 run on Blackwell through TE's flash backend, for any head dim: the forward mask is wrong whenever FA4 is selected. It is worth reporting upstream (TE should pass `None`, or FA4 should accept -1).
13. **`--get-mismatch-metrics` needs `--custom-tis-function-path`** (assert at startup). Dropped it. With `--use-tis`, miles still logs `train/train_rollout_kl`, `train/train_rollout_logprob_abs_diff`, `train/tis*` and `train/ois`.

## Qwen3.5 verdict

miles runs Qwen3.5 hybrids correctly on B200, with one caveat that needs our patch:
- Architecture: supported natively (`miles_plugins/models/qwen3_5.py`). GDN layers via fla `chunk_gated_delta_rule` (fla 0.5.2), short conv via fla with causal-conv1d's CUDA backward (`Linear-attention short conv backend: mix` in the logs; the "mix" choice requires causal-conv1d's backward to import). There is no pure-torch fallback: without fla the layer raises at construction. So fla is used whenever it runs.
- Packing: `thd` + dynamic batch; `cu_seqlens` goes into both the conv and the recurrence, so state resets at sample boundaries.
- VLM checkpoint: text-only training. Vision stays in SGLang, frozen and never synced, and the HF export needs the frozen tensors added back (scripted).
- Full-attention layers: the recipe's `--attention-backend flash` is broken on Blackwell in the v0.1.3 image (TE -> FA4 window bug, item 12). With the runtime fix it is correct (logprob agreement 0.012 abs, KL 4-5e-4).
- No Gemma fallback needed.
14. **`run_qwen3_4b.py`'s `--load <converted torch_dist>` doesn't start in v0.1.3.** Repro job 364322 died at startup: `AssertionError: the trainer restored rollout 0, but .../Qwen3-4B-Base_torch_dist/rollout/0 does not exist; a run saved before the rollout-side state moved into one directory per rollout cannot resume`. The script is stale relative to the checkpoint layout. Fix: pass the converted checkpoint only as `--ref-load`, which is what `run_qwen3_dense.py` and the fully async example do; the actor initializes from it when `--load` has no checkpoint. Lost ~5 min of node time.
15. **Recipe repro paused by scheduling policy.** Repro 364364 (Qwen3-4B-Base, `run_qwen3_4b.py` flags + true-on-policy README batch 64x16 at 2048 tokens; flash backend with the FA4 fix): HF->torch_dist 90 s; step 0 raw_reward 0.160 (published baseline curve ~0.13-0.15 at step 0), step-0 AIME-2024 avg@16 0.010 (published 0.03-0.067). Step 0 took 710 s (rollout 26 s, `train_time` 598 s of which actor train 346 s; the rest is old-logprob and ref-logprob forwards). At that rate the 40 steps would take ~8 h, more than the remaining budget. The script's default layout for Qwen3-4B (TP=2 x CP=4 = 8 GPUs, DP=1, full recompute, colocated) is a poor fit for 2048-token samples, but it is the published recipe. Cancelled after step 0 to free the node for the W1-S shared runs (coordinator policy). To resume within budget, a ~12-step run (~2 node-h at this rate) would cover the published curve's early rise (0.15 -> ~0.25 by step 12-15).
16. **SHARED_W1 rev. 1 and rev. 2 applied.** `--rollout-max-prompt-len 2048` (miles drops longer prompts rather than truncating; none are dropped at 2048); `--apply-chat-template-kwargs {"enable_thinking":false}` (rendered prompt checked: it ends with `<|im_start|>assistant\n<think>\n\n</think>\n\n`); `--rollout-max-response-len 16384`. `--max-tokens-per-gpu` raised from the recipe's 9216 to 18432 so that one full sample fits a micro-batch. Recommended arm: `configs/miles/w1-S-recommended.args` (diffs in EQUIVALENCE.md).

## Proposed changes to SHARED_W1

- **Staleness is not comparable across libraries as written.** "The library's recommended async setting" means *unbounded* for miles (no `--max-weight-staleness`; observed max 4 versions, bounded only by the 2x buffer). If another library caps it at 1, the off-policyness differs by 4x. Either keep it (and plot `staleness_max` next to reward) or add a shared-arm cap, e.g. max staleness 2 (miles: `--max-weight-staleness 2 --async-submit-within-staleness`), leaving the recommended arm uncapped.
- **Name the attention kernel in results.** On B200 the libraries' default attention paths differ (miles: TE -> FA4, which needed a fix). A per-run `train_attention_backend` field in meta.json would make kernel bugs like item 12 visible across libraries.
- **Checkpoint layout for eval.** `eval.sbatch` assumes `checkpoint-<step>` dirs. Worth stating in SHARED_W1/SCHEMA that each library provides that layout, with complete HF checkpoints (a VLM checkpoint must include the frozen vision weights for vLLM to load it).

### W2 verdict

miles v0.1.3 cannot train W2 on B200 as shipped. Its in-process Harbor path runs local Apptainer boxes from inside its container once the sandbox runtime is configured (libs, `APPTAINER_IGNORE_FAKEROOT_COMMAND`, `mount proc = no` + /proc bound in), and episodes complete at the shared budgets. But the first optimizer step OOMs: the only attention backend that is correct on B200 (`unfused`) can't hold 65k-token episodes (miles-020). On top of that, the shipped fully async agentic flags fail miles' own validation (miles-019, fixed with `--no-namespaced-radix-cache`). The 35B-A3B W2 run was not attempted: same attention backend, at TP2 with 8 heads per rank and no packing, so it would OOM sooner. No held-out evals (no checkpoint).
