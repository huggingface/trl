### Architecture

- Three processes launched by `uv run rl @ cfg.toml` (`src/prime_rl/entrypoints/rl.py`): a vLLM inference server (`inference`), an `orchestrator` (CPU: dispatches rollouts through verifiers env worker pools, scores, computes advantages, packs micro-batches) and a `trainer` (torchrun, FSDP2). Single node: `[deployment] num_train_gpus / num_infer_gpus`; GPUs are split from `CUDA_VISIBLE_DEVICES` (inference first, `utils/process.py:partition_gpus`).
- Training backend: FSDP2 over PrimeRL's own model implementations (`src/prime_rl/trainer/models/`, torchtitan-style); "other architectures fail at trainer setup" (README). Defaults: `optimization_dtype = float32` (fp32 master weights), `reduce_dtype = float32`, bf16 compute, `offload = "optimizer"` (AdamW state on CPU), full activation checkpointing, `torch.compile` on, `attn = "auto"` (FA4 on sm_100).
- Inference: vLLM 0.32.0 with prime-rl's vLLM plugin (`prime_rl.inference.patches`), token-in/token-out through `/inference/v1/generate`. Weight sync: NCCL broadcast by default (`rl.py:auto_setup_weight_broadcast`), filesystem for LoRA.
- Loss (`src/prime_rl/trainer/rl/loss.py`, `docs/algorithms.md`): default `[trainer.loss] type = "ipo"`: importance-weighted PG `-A * pi/mu`, tokens masked when `|pi(y) - mu(y)| > eps` (eps 0.3, probability difference, not ratio), ratio capped at 1e4. Alternatives: `icepop` (ratio band [0.2, 5]) and `custom` (user function, the documented way to get a PPO clip). There is no built-in PPO ratio clip. The rl term is `sum(token losses) / N_rl` where `N_rl` is the global count of rl tokens in the step (token-level aggregation), and zero-advantage tokens are removed from the rl component and its denominator (`orchestrator/train_sink.py:_prune_zero_advantages`). No KL, no entropy bonus.
- Advantage: `algo.type = "grpo"` = reward minus group mean, no std normalization ("DR-GRPO without std normalization", `docs/algorithms.md`).
- One optimizer step per batch, always ("Because our trainer is asynchronous, we perform only one gradient step per batch", `examples/basic/hendrycks-sanity/README.md`). The step's samples are packed into micro-batches of `trainer.model.seq_len` tokens and gradient-accumulated.

### Async / off-policy

- Fully async by default (`docs/algorithms.md#async-training--staleness`): trainer step n trains on rollouts sampled by policy n-1 or older. The orchestrator's dispatcher may run at most `TARGET_LAG = 1` shipped batch ahead of the policy version the inference server holds (`orchestrator/orchestrator.py:104`, hard-coded), and pauses dispatch beyond that.
- Rollouts are never cancelled. Weights are updated in flight, and vLLM labels every sampled token with the policy version that produced it, so one completion can mix versions.
- `orchestrator.max_staleness` (default 8, live-updatable) bounds *token* staleness: tokens sampled more than 8 versions before the version being trained on are masked out of the loss; a sample is dropped only when no token is left. With the 1-batch lead, staleness in practice is 1-2 for short rollouts and grows only for completions that span several trainer steps.
- Batch semantics: `orchestrator.batch_size` counts *samples* (rollouts for single-turn), must be divisible by `group_size`. With the default `constant_trainer_batch_size = true`, zero-advantage rollouts are pruned *before* they enter the pending batch, so every step trains on `batch_size` rollouts that carry signal, and the orchestrator generates as many groups as needed to fill it (dynamic-sampling-like). With `false`, a step takes the next `batch_size` rollouts as they come and prunes zero-advantage tokens after selection, so the trained batch shrinks.
- Concurrency is adaptive (`[orchestrator.concurrency]`, driven by vLLM KV pressure, max 1024 in flight by default).

### Recipes and published numbers

- `examples/basic/reverse-text`: Qwen3-0.6B SFT then 20 RL steps, batch 128 = 8 prompts x 16, 128 completion tokens, lr 3e-6, 1 infer + 1 train GPU. Published: eval reward ~0.05 for the base model and "~0.8" for the RL'd model (`PrimeIntellect/Qwen3-0.6B-Reverse-Text-RL`), W&B logs linked. Starting from the SFT checkpoint, the RL run is the CI integration test (`configs/ci/integration/reverse-text`).
- `examples/basic/hendrycks-sanity`: the "Hendrycks sanity check" from Defeating the Training-Inference Mismatch (https://huggingface.co/papers/2510.26788): Qwen3-1.7B on `mikasenghaas/Sanity-Test-R1D-1.5B` (MATH problems R1-Distill-1.5B solves 20-80% of the time), batch 512 = 64 prompts x 8, seq_len 8192, lr 1e-6 (default), 4+4 GPUs, 5000 steps, AIME24 eval every 50 steps. Published target: "A reliable algorithm should push training accuracy on this perfectible subset above 95%". No curve or step count for reaching it is in the repo.
- `examples/advanced/qwen3-30b-a3b/math.toml`: Qwen3-30B-A3B-Thinking on `i3_math`, batch 512 x group 8, 32k tokens, lr 1e-6, `max_staleness = 8`, 2+2 nodes. No published numbers in the repo.
- `math_env` (`deps/prime-envs/environments/math/math_env`): prompt prefix "Solve the following math problem. Explain your reasoning and put the final answer in \boxed{}.", reward = `vf.verify_boxed_math_answer` (math-verify) with an LLM-judge fallback that is ON by default and calls Prime Inference, i.e. needs a Prime API key. For any run on our cluster it must be turned off (`env.taskset.task.judge = null`).

### Qwen3.5 (code reading; runtime check in a later section)

- Own implementation `src/prime_rl/trainer/models/qwen3_5/` (dense and MoE, text and VLM). The VLM checkpoint (`Qwen3_5ForConditionalGeneration`, has `vision_config`) loads into the composite model; without `[model.vlm]` the trainer logs "Training a VLM checkpoint on text-only data; freezing the vision encoder" (`trainer/model.py:configure_trainable_parameters`). Tied embeddings for the small checkpoints are handled explicitly (`modeling_qwen3_5.py`, comment about 0.8B-4B shipping no `lm_head`).
- Linear-attention layers (`trainer/models/layers/gated_delta_net.py`) import `fla.ops.gated_delta_rule.chunk_gated_delta_rule`, `fla.modules.conv.causal_conv1d` and `fla.modules.FusedRMSNormGated` at module import time. There is no torch fallback: without fla the trainer fails to import, it can't silently go slow. The `causal-conv1d` CUDA package is not used by the trainer (it uses fla's Triton conv), and vLLM uses its own GDN/conv kernels, so it isn't needed here.
- Packing: micro-batches are packed sequences; `seq_lens` are passed into the model, turned into `cu_seqlens` (`utils/sequence.py:get_cu_seqlens_from_seq_lens`), and both `causal_conv1d(..., cu_seqlens=...)` and `chunk_gated_delta_rule(..., cu_seqlens=...)` get them, as does flash attention for the full-attention layers. So the conv window and the recurrent state reset at every sample boundary by construction.

### Multi-turn and W2 (agentic coding, Harbor)

- Generic Harbor support lives in verifiers v1: `deps/verifiers/verifiers/v1/tasksets/harbor/taskset.py` (`HarborTaskset`). It runs `harbor download <dataset> --export` (harbor CLI from `verifiers[harbor]`, which prime-rl depends on), parses each `task.toml` with Harbor's own models, uses `instruction.md` as the prompt and the task's docker image / Dockerfile / compose as the box, and grades by uploading `tests/` and running `bash /tests/test.sh`, reading `/logs/verifier/reward.json` (or `reward.txt`). Task timeouts are ignored by default. Datasets come from a Harbor registry (`--repo`, `registry_path`, `registry_url`); a local directory of 1,004 tasks needs a `registry.json` or a 10-line `load()` override.
- prime-envs wraps it: `environments/terminal/terminal_bench_2` (TB2, 89 tasks), `pi_terminalbench2_1` (TB 2.1, 82 tasks), `openthoughts_tblite`, `tmax`; plus many SWE envs (swebench_verified/pro, r2e_gym, deep_swe, ...).
- Harness is independent of the taskset (`env.agent.harness.id`): `bash` (default, verifiers' own chat-completions tool loop), `terminus_2` (installs Harbor 0.25.0's Terminus in the box), `opencode`, `pi`, `claude_code`, `codex`, `mini_swe_agent`, `rlm`. The harness runs inside the sandbox and reaches the policy through an interception server plus a tunnel.
- Sandbox backend: default is Prime Sandboxes (`runtime: PrimeConfig`, `runtimes/backends/prime.py`, needs `PRIME_API_KEY`) plus the Prime tunnel; also `docker` and `subprocess`. The backend is pluggable: `runtime.type = "custom"` + `import_path` to a `RuntimeBackend` subclass (`runtimes/base.py`: `start`, `exec` with streaming, `write`, `cleanup`; flags `SUPPORTS_TASK_IMAGES`, `SUPPORTS_PORT_EXPOSURE`).
- Feasibility: (a) HF Sandboxes = write a `RuntimeBackend` (prime.py is 572 lines, so a few hundred lines) plus a reachable tunnel for the interception server; doable but real work. (b) OpenEnv's Harbor server does not fit: verifiers expects a shell-exec box with the harness and grader inside it, not a reset/step API. It would need either a backend built on the server's exec/file endpoints or a custom Harness/Task driving reset/step. Without either, W2 on prime-rl means Prime Sandboxes (paid, external) or docker on the node.
- Multi-turn tokenization is token-in/token-out through renderers (`[orchestrator.renderer]`, auto-picked from `MODEL_RENDERER_MAP`): each turn is appended to the exact previous prompt+completion ids (`bridge_to_next_turn`), no re-tokenization, and each trace branch becomes one training sample with env/tool tokens masked.
