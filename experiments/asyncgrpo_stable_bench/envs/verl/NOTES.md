## Research (task 1)

### Install

- verl drives its environment with `uv` and one committed universal `uv.lock`. A run picks backends as extras: `uv sync --frozen --all-packages --extra vllm --extra fsdp` (`docs/start/install.rst`, `pyproject.toml`). Their examples go one step further and wrap every command in `uv run --frozen --all-packages --extra vllm --extra fsdp`, with Ray workers started through `ray_kwargs.ray_init.runtime_env.py_executable`.
- We keep the venv outside the repo with `UV_PROJECT_ENVIRONMENT=/fsx/amine_dirhoussi/envs/bench-verl` and launch with the venv's `python` plus `VERL_USE_UV=0`, `py_executable=null` (documented fallback in install.rst: Ray workers then inherit the driver interpreter). Same locked packages, no per-launch `uv run` resync.
- Locked stack for `vllm + fsdp`: torch 2.11.0+cu130, vLLM 0.24.0 (PyPI cu130 wheel), transformers 5.9.0 (project-wide override), flash-attn 2.8.3 (verl wheelhouse, prebuilt), `flash-linear-attention==0.5.2` + `fla-core==0.5.2` (in the `fsdp` extra), liger-kernel, cupy-cuda13x (NCCL weight sync), TransferQueue (git, always installed). Python 3.12 only.
- `causal-conv1d` is not in the lock. We add it after the sync (built against the venv's torch with CUDA 13.0).
- `math-verify` comes from the `math` extra.

### Async mode for a disaggregated 4+4 split: V1 `separate_async`

verl 0.9.1 has three async options:

1. `verl/experimental/one_step_off_policy` (`docs/advance/one_step_off.md`, last updated 2025-07): fixed one-step lag, standalone rollout GPUs.
2. `verl/experimental/fully_async_policy` ("v0 fully async", `docs/advance/fully_async.md`, 2026-05): Rollouter + MessageQueue + Trainer on separate GPUs, staleness via `async_training.staleness_threshold`, partial rollout. Ships a 4+4 FSDP2 DAPO script (`shell/dapo_7b_math_fsdp2_4_4.sh`). Published: 2.35-2.67x over colocated sync on Qwen2.5-Math-7B DAPO at 32-128 H20s.
3. The V1 trainer (`docs/advance/v1_async_trainer.md`, 2026-09-16) under the main entry point `verl.trainer.main_ppo` with `trainer.use_v1=True`: modes `sync`, `colocate_async`, `separate_async`.

We use **V1 `separate_async` with `actor_rollout_ref.hybrid_engine=False`**. Why:

- `main_ppo` logs that the non-V1 path is deprecated ("Legacy trainer `main_ppo_v0.py` is deprecated ... set `trainer.use_v1=True`", `verl/trainer/main_ppo.py:186-191`). V1 is the main path; one-step-off and fully-async are still in `experimental/`.
- In the V1 doc's own benchmark (Qwen3.5-35B-A3B, DAPO-Math-17k, 4 nodes), `separate_async` is the fastest mode: 14.10 h for 150 steps vs 14.72 h `colocate_async` and 22.79 h `sync`. That benchmark is on a Qwen3.5 hybrid, which is the architecture we run.
- `separate_async` is the disaggregated mode: dedicated rollout GPUs, streaming one PPO mini-batch at a time, partial rollout (aborted generations resume after a weight update), NCCL weight sync via `checkpoint_engine.backend=nccl` (required).
- By default it also keeps sleeping "hybrid" vLLM replicas on the trainer GPUs (used for validation and the optional `enable_switch` GPU lending). `hybrid_engine=False` removes them, so the trainer GPUs never run inference. That is what our fixed 4 inference + 4 train split asks for. The doc says this setting is "mainly useful for v0/v1 comparisons and for dedicating all trainer GPUs to training", so it's a supported setting, but not their default. Recorded as a deviation.
- Staleness defaults: `trainer.v1.sampler.max_off_policy_threshold=8` (model versions from first token to training) with `max_off_policy_strategy=drop`, `num_warmup_batches=1`, `parameter_sync_step=4` (weight sync every 4 mini-batches). The e2e test (`tests/special_e2e/run_v1_separate_async_opd.sh`) uses the same values plus `algorithm.rollout_correction.bypass_mode=True` (PPO ratio against the rollout logprobs, no trainer recompute of old logprobs).

### Training backend: FSDP2

- `docs/start/install.rst`: FSDP/FSDP2 for research and prototyping, Megatron for scalability. `docs/perf/perf_tuning.rst:247`: "FSDP2 ... is recommended for models with transformer architecture".
- Every Qwen3.5 example in tree uses `actor.strategy=fsdp2` (`examples/grpo_trainer/run_qwen3_5_2b_openr1_fsdp.sh`, `run_qwen3_5_27b_fsdp.sh`, `run_qwen3_5_35b_fsdp.sh`). The code default is still `strategy: fsdp` (`verl/trainer/config/engine/fsdp.yaml:79`), so we set `fsdp2` explicitly. Megatron is used upstream for MoE and >30B. For 2B-9B dense we follow the FSDP2 examples.
- FSDP master weights: fp32 params, `mixed_precision.param_dtype=bf16`, `reduce_dtype=fp32` (`_generated_ppo_trainer.yaml:71-72`).

### Qwen3.5 support (code reading; runtime check below)

- `verl/models/transformers/monkey_patch.py:500-542` patches `Qwen3_5GatedDeltaNet.forward`, the decoder layer and `Qwen3_5ForConditionalGeneration.forward` when `model_type == "qwen3_5"`.
- Packing (`use_remove_padding=True`) in the linear-attention layers is boundary-aware (`verl/models/transformers/qwen3_5.py:146-336`):
  - Short conv: with `causal_conv1d` installed, it is called with `seq_idx` built from `cu_seqlens` (`fla.ops.utils.prepare_sequence_ids`), so the conv window does not cross samples. Without it, verl splits the packed tensor per sample and runs the torch conv on each segment (correct, slower). This is better than stock transformers, whose torch conv ignores boundaries.
  - Gated delta rule: if `chunk_gated_delta_rule` (fla) accepts `cu_seqlens`, it is passed, so the recurrent state is reset per sample. Otherwise verl splits per sample and calls the kernel once per segment (correct, slower).
  - Packed + cached forward raises; packed with batch size != 1 raises.
- Upstream ships `examples/grpo_trainer/run_qwen3_5_2b_openr1_fsdp.sh` (Qwen3.5-2B GRPO, fsdp2, but `use_remove_padding=False`, multimodal data) and `run_qwen3_5_27b_fsdp.sh` (`use_remove_padding=True`).

### W2 (multi-turn agents)

- Agent loop: `verl/experimental/agent_loop/agent_loop.py`. Subclass `AgentLoopBase`, implement `async run(sampling_params, **kwargs)`, register with `@register(name)` or a YAML list in `rollout.agent.agent_loop_config_path`. The loop is picked per sample from the `agent_name` column (default `rollout.agent.default_agent_loop`). Generation is token-in/token-out through `self.server_manager.generate(request_id, prompt_ids, sampling_params)` with sticky routing per request id (prefix cache). Multi-turn tokens use "continuous token" helpers (`ct_merge_assistant_token` keeps sampled tokens with mask 1, `ct_merge_context_msg` appends only the new tool/user tokens with mask 0, per-model boundary builders in `verl/utils/tokenizer/continuous_token.py`). Setting `AgentLoopOutput.reward_score` skips the reward manager, so an env reward can be passed straight through.
- Works with the async trainers: fully-async subclasses `AgentLoopManager` (partial rollout is transparent to the loop) and V1 dispatches all rollouts through AgentLoop.
- Existing integrations: no Harbor, Terminal-Bench, OpenEnv, OpenHands, mini-swe-agent, E2B or SWE-bench code in verl. `verl/tools/` is only the tool base classes. Sandbox Fusion is used as a code reward scorer and in a tutorial `SandboxTool`. verl-recipe has `swe_agent/` (about 2.5k LOC: runs SWE-agent in local Docker, with an OpenAI-compatible model proxy in front of verl's vLLM) and `retool`, `langgraph_agent`.
- Adapter estimate for an OpenEnv Harbor server: one `HarborAgentLoop(AgentLoopBase)` of about 250-400 LOC (reset over HTTP, generate, parse action, step, merge observation tokens with mask 0, close the episode in `finally`, set `reward_score`), plus a data-prep script turning task ids into parquet rows (about 80 LOC) and a config (about 50 LOC). No verl core changes needed. If Harbor's Terminus-2 has to drive the episode itself (it calls an OpenAI API), the `swe_agent` model-proxy pattern applies instead: more code and re-tokenization risk. Pitfalls: sandbox concurrency limits and cleanup, observation truncation within `response_length`, all-or-nothing reward needing difficulty filtering, long episodes spanning several weight versions under partial rollout.

## Proposed changes to SHARED_W1

1. **Name the weight-sync frequency as a knob.** "Optimizer steps per batch: 1" and "the library's recommended async setting" leave open how many optimizer steps run between weight syncs. verl's default is 4 (`parameter_sync_step`); the verl shared arm uses 1 so that verl's step is one 32-prompt optimizer step followed by a sync. Suggest a row "weight sync: after every optimizer step (shared arm)" and having each library record its value.
2. **Say whether dual-clip is allowed.** verl applies dual-clip PPO (`clip_ratio_c=3.0`, caps the loss of negative-advantage tokens at 3|A|) by default, on top of clip 0.2/0.28. It's kept at the default in the verl shared arm. If other libraries don't do it, the shared row should either allow it explicitly or ask for it off (`clip_ratio_c` can't be disabled in verl, only set very large).
3. **Define "step" and checkpoint steps in optimizer steps for the recommended arm.** A library whose natural step groups several optimizer steps (verl recommended: 4 per global step) can only checkpoint on its own step boundaries (verl: optimizer steps 48/96/144/192/200 instead of 50/100/150/200). Suggest "nearest checkpoint at or before 50/100/150, plus the final step".
4. **Don't compare `logprob_mismatch_kl` across libraries without a definition.** verl in bypass mode only exposes `actor/ppo_kl` = mean(logp_vLLM - logp_trainer) on the train batch, which mixes engine mismatch with policy lag. Suggest the schema says "KL(inference || trainer) on the same weights" and lets libraries that can't isolate it write null.
5. **Report startup separately from step time and say where the venv lives.** verl takes ~16-20 min from job start to its first step on b200 with the venv on /fsx (cold imports in every Ray worker, then vLLM compile + CUDA-graph capture). Either all libraries stage their venv on local `/scratch` or `first_step_s` is reported as-is with that caveat.

## W2

### Approach

verl ships no Harbor / terminal-task integration, but it ships the agent-loop API for exactly this (`AgentLoopBase` + `rollout.agent.agent_loop_config_path`). `configs/verl/w2_agent_loop.py` (~300 lines incl. docstrings and the launcher helpers; the AgentLoop itself ~170) is the adapter. No verl source change.

- **Same environment as TRL.** Each episode is one `run_rollout` on the OpenEnv Harbor server TRL uses (`openenv harbor serve` from `bench-trl-w2`, harbor-local-sif tasks, `W2_SANDBOX=singularity`, `APPTAINER_BIND=/etc/resolv.conf`, terminus-2 host-side, 600 s agent budget, 30 calls, 8192 output tokens). OpenEnv is not in verl's venv, so the agent loop runs the call in a small client process with the W2 venv's python (termgrade_env's `RecordedHarborSession`, which also writes the per-episode phase record).
- **Generation through verl, not Harbor's capture.** Harbor's capture would return per-call token ids from a vLLM it can reach over HTTP, but verl's rollout servers abort in-flight requests at every weight sync (`checkpoint_engine/base.py:522`), which would hand terminus-2 truncated replies. So the rollout's engine URL points at a proxy inside the agent-loop worker (`/ep/<episode id>/v1/chat/completions`), and each terminus-2 call becomes `self.server_manager.generate(...)`: verl's load balancer, sticky routing per episode (prefix cache), and `FullyAsyncLLMServerClient`'s partial-rollout resume across weight syncs. Sampling is verl's (T 1.0, top_p 1.0, top_k -1, repetition_penalty 1.0); terminus-2's own sampling params are ignored.
- **Tokens are verl's Continuous Token path**, as in its ToolAgentLoop: the first call is rendered with the chat template (`enable_thinking=false`), every later call appends only the new messages (`ct_merge_context_msg`) to the exact tokens already sampled (`ct_merge_assistant_token`). So an episode is **one sample** (prompt = first call's prompt, response = everything after, mask 1 on sampled tokens, logprobs from vLLM), not one sample per call as in TRL. The model sees its own sampled tokens as history; TRL/Harbor re-render the chat each turn (Qwen3.5 renders a past assistant turn differently), so turn 2+ prompts are not token-identical to TRL's. Same choice as prime-rl (renderer bridging). If a request's history were not an append of the previous one, the episode would continue as a new sample (verl's `list[AgentLoopOutput]`); with summarisation off this shouldn't happen (counted per episode, `samples`).
- **Harbor's engine probe.** Harbor probes every new engine URL (one per episode here) with a couple of few-token or tool-manifest requests; the proxy answers those without the model, so Harbor runs at its `text` capture level ("eval" tier: reward + trace, no token capture). The token record is the proxy's.
- **Startup.** `openenv harbor serve` exits if its `--llm-url` is unreachable at startup, and verl's servers only exist once training starts, so the launcher runs a stand-in (`w2_agent_loop.py stub`) for that check and stops it once the servers are up.
- **Reward / failures.** `reward_score` = the verifier's score, so verl's reward manager is skipped. An episode the verifier never scored returns no outputs (empty list, which the V1 TQ worker accepts), so it is excluded from training and from its group's baseline (SHARED_W2). Raising instead would mark the whole group failed and verl would evict and refill it (SkyRL-like); not used.
- **Concurrency.** V1 `separate_async` keeps up to 2 batches (16 prompts = 128 episodes) dispatched (1 warmup batch + the next one each step). Each of the 8 agent-loop workers gets one prompt per batch, and a semaphore of 8 episodes per worker caps the run at 64 live boxes (SHARED_W2), FIFO, so the oldest batch's episodes start first.
- **Harbor servers:** `HARBOR_SHARDS=8` (episodes round-robin across 8 single-threaded servers, envs/trl/W2_STEP_TIME.md cause 1) and `TERMINUS_MAX_TURNS=1` (terminus-2 stops at the 30-call budget instead of re-asking until 600 s, cause 4). Both are options of the shared launcher logic; TRL's local run 366992 used neither, so episode wall and step time are not directly comparable to it.
- **Config** `configs/verl/w2-M.yaml`: W1-M shared with `train_batch_size=8`, `ppo_mini_batch_size=8` (x n=8 = 64 episodes = one optimizer step, `parameter_sync_step=1`), `max_model_len=65536` (prompt 8192 + response 57344 budgets), `ppo_max_token_len_per_gpu=65536` (one whole episode per micro-batch), checkpoints every 20 (`hf_model` included), 60 steps, data shuffled with seed 42 (28 train tasks, so tasks repeat ~17 times). Everything else (GRPO group mean, no std, clip 0.2/0.28 + dual-clip 3.0, bypass mode, token-mean, lr 1e-6, max staleness 8 / drop, NCCL sync, FSDP2 fp32 master) is the W1 shared arm. GRPO baseline: mean over the group's samples, which is the mean over episodes when every episode is one sample.
- Launcher `launch/verl/w2.sbatch` (job name `w2local-verl`): Harbor shards + box cleanup copied from `launch/trl/w2.sbatch` SANDBOX=local, then verl's `common.sh` + `main_ppo`. Collect: `collect/verl.py` then `collect/verl_w2.py` (episodes.jsonl; per-step `trained_tokens` = SHARED_W2 per-call count, `forwarded_tokens` = verl's `perf/total_num_tokens`, `prefix_share_ratio`).
