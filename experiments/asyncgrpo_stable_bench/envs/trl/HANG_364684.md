# Hang in trl-w1-S-shared-364684 (heartbeat stale after step 9)

**Root cause.** Our math reward. It calls math_verify with its timeouts turned off whenever it isn't on the main thread (`workloads/math/reward.py:37`), and AsyncGRPO always runs a sync reward on a thread (`asyncio.to_thread`, `trl/experimental/async_grpo/async_rollout_worker.py:1339`). A completion whose last box is a big power tower (`\boxed{10^{10^{10}}}` reproduces it) sends `verify` into sympy's `Integer._eval_power`, which works on a huge exact integer in C and keeps the GIL for long stretches. Every other thread in the rollout worker child, the asyncio event loop included, stops running: no replies are read, no requests are sent, no heartbeat. After 300 s the trainer's watchdog fires correctly. The span-logging `loop_cls` override is not involved (it reproduces without it), and TRL's loop does nothing wrong, though its watchdog left no trace of where the child was stuck (patch below).

Scripts, logs and stack dumps: `envs/trl/hang364684/`.

Which completion triggered it in 364684 can't be recovered: completions aren't logged (`log_completions=False`, vLLM doesn't log outputs), and the hung group never reached the trainer. The identification rests on the signature matching (event loop dead, child alive, replies unread, missed 15 s stop) and on the repro.

## Timeline from the run files

- Generate spans (`spans-generate-537456.jsonl`, written by our loop after every `/v1/completions` reply): a steady ~50 replies per 5 s right up to the end, last reply at **21:42:02.227**, then nothing. The last 50 are all version 9.
- vLLM: step-9 sync paused at 21:42:06 and unpaused at 21:42:07 (`/pause?mode=keep&clear_cache=false`, then `/resume`). After the resume, vLLM still returned **991** `POST /v1/completions 200` and then got exactly **one** more `GET /metrics`. Before that, the child polled `/metrics` every ~5 s (the control loop's `_metrics_poll_s`).
- vLLM GPUs (`gpu.csv`): 82-96% busy until 21:42:59, 54% in the 21:43:00 bin, 0% from 21:43:05 on. So the ~1000 requests in flight at the freeze drained normally in about a minute and the server then sat idle. No new requests came in: the child was not dispatching.
- Trainer: last metrics row at 21:42:07 (step 9), then it waited on the rollout queue. It printed `Child did not exit within 15s; terminating.` before the traceback, so the stale check fired around 21:47:04 and the last heartbeat was around 21:42:04.

So the child stopped at about 21:42:02-04, a few seconds before the step-9 sync started. It's not the sync and not vLLM. And it's not one coroutine stuck waiting: the generate tasks write a span as soon as their reply arrives, and 991 replies arrived without a single span, so nothing on the child's event loop ran at all. The child also ignored the stop event for 15 s. Both point at the child's main thread starved of the GIL by another thread for 5+ minutes.

The timeline comes from `hang364684/timeline.py` (hopper-cpu job 364713).

## Ruled out

- **Rollout queue full (`queue.put` blocking).** `queue_maxsize` defaults to 1024 (`async_grpo_config.py:374`). `sample/rollout_queue_size` peaked at 825 at step 4 without a hang and was 90 at step 9. The parent raised from the `queue.Empty` branch (`async_grpo_trainer.py:291-295`), so it saw an empty queue. And the child's full-queue waits (`_put_in_buffer`, lines 1002-1022, and the `_groups_to_score` wait at ~868-878) spin on `await asyncio.sleep(0.1)` with the event loop running, so spans would have kept coming.
- **Our span logger (`W1RolloutLoop.generate_one_turn`).** One line-buffered `/fsx` write per reply. It reproduces with that write turned off (below). Parent-side `/fsx` writes (metrics.jsonl, mem-rank*.jsonl) went through normally at 21:42:07.
- **The weight sync / vLLM pause path (incl. the slow `/pause?mode=keep` seen in 364705 and on 2026-10-19).** Not this hang. (1) The child's last span is 21:42:02.2 and its last heartbeat ~21:42:04, both before `/pause` at 21:42:06. (2) The step-9 pause itself was fast: `perf/weight_sync_pause_s` = 0.060 s (all 9 steps of 364684 are 0.05-0.08 s, unlike 364705's 0.3-70 s). (3) After `/resume`, vLLM did resume. It finished and returned all 991 in-flight requests (GPU busy until ~21:43:05), so nothing was stuck in the API server. The client just never read them. (4) The CPU repro reproduces the freeze with no vLLM and no pause at all (fake server, no weight sync). So any overlap with the pause-latency investigation is a coincidence of timing: the trainer syncs about every 35-50 s, so any freeze lands within seconds of some sync.
- **mp.Queue GC stalls over list payloads** (earlier note). Those cost seconds, not minutes, and leave the event loop running between collections.
- **fp32 -> bf16 dtype warnings and `MRotaryEmbedding/ParallelLMHead: Failed to load weights` on every sync.** Unrelated to the hang. Every sync, including the nine good ones, logs them. The dtype warning is vLLM casting the fp32 master weights the trainer sends (`dtype="float32"` + FSDP mixed precision) into its bf16 params. It's harmless for correctness but sends twice the bytes per sync. Worth a separate look (memory note: the PR #7939 checkpoint-dtype work covers the save side, not sync).
- **`ServerDisconnectedError` retries in the first wave.** Startup only and recovered. The live run 364705 shows the same at startup.

## Evidence

### 1. Bad answers keep the GIL (hopper-cpu job 364713, `gil_probe.py`)

`compute_score` runs in a thread, as in the rollout worker. The main thread ticks every 10 ms and gives up after 90 s, and `timeout -s KILL 100` is the backstop.

| box | result |
|---|---|
| `42` | 0.05 s, main thread never stalls |
| `10^{10^{10}}` | **process unresponsive, killed at 100 s** (the main thread never reached its own 90 s check) |
| `9^{9^{9}}` | **killed at 100 s** |
| `10^{10^{8}}` | **killed at 100 s** |
| `(10^{6})!`, `1000000!` | 5.7 s, main thread stalled 2.3 s at a time |
| `\binom{10^{9}}{10^{6}}` | still running at 90 s but the main thread never stalled (pure Python, gives the GIL back) |
| `2^{2^{2^{2^{2}}}}`, `7^{7^{7}} \bmod 10` | well under a second |

On the main thread with math_verify's timeouts on (job 364721, `mainthread_probe.py`), both `10^{10^{10}}` and `\binom{10^{9}}{10^{6}}` return 0.0 after 5.1-5.2 s ("Timeout during comparison"). So SIGALRM can interrupt it. What makes AsyncGRPO hang is that the reward runs off the main thread, where math_verify's timeouts are off.

Two repro artifacts, not related to 364684:

- The first fixed-reward attempt (a `multiprocessing` pool inside `math_reward`) failed with `AssertionError: daemonic processes are not allowed to have children`. TRL spawns the rollout child with `daemon=True`, so no reward function can start processes. That's why the fix below is an async reward instead.
- Control arms with periodic `faulthandler.dump_traceback_later` dumps died with SIGSEGV (exit code -11, job 364750), always on a 20 s dump tick (~40, ~60 and ~80 s in jobs 364731, 364750, 364723). The last dump in 364750 is cut off mid-walk (`File ???, line ???`) while the main thread was in `json.encoder`. faulthandler walks other threads' frames without the GIL, which isn't safe on a busy thread. The control without periodic dumps (`DUMP_EVERY=0`) got past 28k requests and 92 s with the heartbeat at 0 s before a spot preemption (`logs/failed/hang-repro-nodump-364798.preempted1.out`). The one-shot SIGUSR1 dump in the TRL patch only fires on a child that's already about to be killed, so it doesn't have this problem in practice.


## Fixes

### Harness (the fix for the benchmark): async `math_reward`

Make `math_reward` in `configs/trl/w1-S.py` an `async def`. Nothing else changes. TRL awaits async reward functions directly on the rollout child's event loop (`async_rollout_worker.py:1339`, `reward_func(**kwargs) if is_async_callable(reward_func) else asyncio.to_thread(...)`), and that loop runs on the child's main thread. There `compute_score` turns math_verify's SIGALRM timeouts back on (5 s parse, 5 s verify), and job 364721 shows they do interrupt `10^{10^{10}}` (score 0.0 after 5.1 s). The cost is that scoring now blocks the event loop while it runs: a few ms per normal group, at most ~10 s per completion on a pathological one, against a 300 s watchdog. `reward.py` is unchanged, so scores on normal answers stay identical across libraries.

A process pool doesn't work here (daemonic child, see above), and `reward.py` already has the main-thread timeout path, so this is the smallest change. It was applied to `configs/trl/w1-S.py` (and `w1-M.py`) after this run: `math_reward` is `async def` there now.

Other libraries call the same `compute_score`. Whether they're exposed depends on where they call it: on a process's main thread math_verify's 5 s SIGALRM saves them, but in a thread they'd hang the same way. Worth checking each harness's reward wrapper.

### TRL (diagnostics, not the cause): dump the rollout worker's stacks on a stale heartbeat

`_child_main` registers `faulthandler` on SIGUSR1, and `check_health` sends SIGUSR1 to the child before raising the stale-heartbeat error. The child's stacks for every thread then land in the trainer log right before the traceback, so the next hang names its own culprit. faulthandler writes from the signal handler in C, so it works even while another thread holds the GIL. That's exactly what produced the dump above. 41-line diff against 5623e8b63, not part of this directory.

Also for the 1.18 release: TRL's own `trl/rewards/accuracy_rewards.py` (lines 74-78 and 296-300) turns math_verify's timeouts off off the main thread the same way. Since AsyncGRPO always runs sync rewards with `asyncio.to_thread`, `AsyncGRPOTrainer` + `accuracy_reward` is exposed to this exact hang. Making `accuracy_reward` async is **not** a general fix: GRPOTrainer runs async rewards on a daemon thread (`start_event_loop_in_daemon`, `trl/trainer/grpo_trainer.py:799`), so it would lose the timeouts there. The two trainers put sync and async rewards on opposite threads. Options for a separate PR: (a) document in the AsyncGRPO docs that a sync reward runs in a worker thread with no signal-based timeouts, and that a math_verify reward should be `async` there; (b) in AsyncGRPO, run sync reward functions on the child's main thread (the event loop) instead of `asyncio.to_thread`, which restores the SIGALRM timeouts for every math_verify reward but lets a slow reward block generation. A subprocess pool inside a reward isn't an option because the rollout child is daemonic. That needs a separate PR and a decision. It isn't in this patch.

## Live run 364705 (recommended arm)

At risk. It runs the same `math_reward` → `compute_score` path in a thread, so any completion with a big power tower in its last box will freeze it the same way. The odds are per completion, so it may or may not hit one in 200 steps (364684 hit one in ~5300 replies). It was healthy when I checked (step 1, spans flowing at 22:09). Nothing was done to it.
