## Findings from reading the code

1. **No transformers branch needed.** transformers 5.20.2 (PyPI, what `envs/trl/install.sh` already resolves) ships `DistributedConfig(ep_size=...)`, the `efsdp` expert mesh, token dispatch (`ep_dispatch_experts`) and the Trainer support for load-time sharded models (`is_distributed_loading_by_transformers`: no accelerate wrap, `save_only_model` required). `install.sh` pins `transformers>=5.20.2`.
2. **Ranks of one EP group train on different data.** In `EpDispatchExpertsParallel`, each rank sends its own tokens to the expert owners by all-to-all; only TP ranks share a batch (`transform_inputs_pre_forward` slices the TP replicas so each token is dispatched once). Dense params are FSDP-sharded over `fsdp` (divide by `fsdp_size`), experts over `efsdp = fsdp * tp / ep` with `set_gradient_divide_factor(fsdp_size)`, so both reduce to the mean over `fsdp_size` batches. Data-parallel size is `world / (tp * pp)` = `fsdp_size`, independent of `ep_size`. With `DistributedConfig(fsdp_size=8, ep_size=8)` (tp=1, pp=1) that is 8 = `accelerator.num_processes`, so `samples_per_step`, `TokenBudgetBatcher(num_processes)`, `max_concurrent_rollouts`, `tokens_per_rank` in the loss and the metric reductions are already right. What would be wrong is TP or PP: TP ranks share a row, so the batcher would have to build `world / tp` rows. AsyncGRPO refuses `tp_size > 1` (PR 1) rather than half-supporting it; transformers already refuses token dispatch with `pp_size > 1`.
3. **Weight names line up with vLLM.** The Qwen3.5-35B-A3B checkpoint stores experts fused (`model.language_model.layers.N.mlp.experts.gate_up_proj` `[E, 2I, H]`, `down_proj` `[E, H, I]`), the same names and layout as transformers' parameters, and vLLM 0.33's `RoutedExperts.load_weights` accepts fused 3D tensors (`chunk(2, dim=1)` for gate/up). `_streaming_iter` already calls `full_tensor()` per parameter, which all-gathers over the expert mesh (`efsdp x ep`) as well as `fsdp`, one parameter at a time (largest: one layer's `gate_up_proj`, 256 x 1024 x 2048 fp32 = 2.1 GB).
4. **Mixed precision** follows main's `examples/lfm2_5_moe_research_agent/1_sft.py`: `dtype="float32"` + `DistributedConfig(..., fsdp_mixed_precision=True)` (bf16 params for compute, fp32 reduce, fp32 master + Adam), launched with `torchrun` (no accelerate FSDP config: the model is already sharded).

    - **How LoRA reaches vLLM.** AsyncGRPO has two paths: adapter-only (server started with `--enable-lora`, single replica) and merged (fold the adapter into the base weights, stream every base weight over NCCL, unfold). The server here has DP=4, where `select_adapter_sync` always falls back to merged (a loaded adapter would reach only one DP replica), and Qwen3.5-MoE LoRA serving in vLLM is untested anyway.     - **LoRA params under load-time sharding.** PEFT is applied after transformers' `fully_shard`, so lora_A/B are plain replicated tensors next to DTensor base weights. transformers' Trainer already handles that (`_sync_replicated_trainable_parameters`: broadcast from rank 0 at train start, AVG all-reduce of their grads per optimizer step, same mean as FSDP's). Reproduced on CPU/gloo with 2 ranks and the tiny Qwen3.5-MoE (`run/lora_merge_check.py`, job 366048). Under Accelerate's FSDP this never happens (it wraps after PEFT, so the adapters are DTensors too). **Fix** (`_sync_weight_merged`, AsyncGRPO and AsyncDistillation, identical): merge and unmerge under `torch.distributed.tensor.experimental.implicit_replication()`, which treats the replicated delta as `Replicate()` so each rank adds its own slice, no communication. (A first run showed 0.7 differences: my check hadn't broadcast lora_A, which PEFT inits differently per rank; the trainer broadcasts before the first sync.) Own PR.
    - **LoRA on the fused experts is not supported.** PEFT can target 3D expert parameters (`target_parameters=["mlp.experts.gate_up_proj", "mlp.experts.down_proj"]`, `ParamWrapper`), but under EP: (a) the expert parameter is a DTensor sharded on the expert dim and token dispatch runs the experts' original forward on the local slice, while ParamWrapper's delta would have the global expert count, so the adapter would need to be EP-sharded the same way (local experts only) and the dispatch path would have to apply it; (b) merging needs a 3D delta added into a sharded DTensor expert (implicit replication would do it if (a) holds); (c) AsyncGRPO's adapter-only path rejects `target_parameters` on purpose (vLLM's fused-MoE LoRA format), so it would be merged sync only. That's transformers/PEFT work (EP-aware ParamWrapper), not a TRL change.
    - Under PEFT the merged stream also carries the frozen vision tower (`_iter_vllm_named_params` inverts its filter). Checked that a text-only vLLM engine (`--limit-mm-per-prompt` 0) takes those tensors (job 366052, `PUSH_VISUAL=1 run/impl_check.py`): 69 tensors pushed, no error, vLLM vs perturbed transformers 0.0003 mean / 0.0010 max after the push.
